# 高専過去問クラウド分析・KNOT Study改善ブリーフ

## 最上位理念：本人専用・世界最高峰の高専入試対策
この教材の第一の利用者・開発上の基準は、開発者本人である中学3年生の受験生。一般的な中学生向け教材に平均化せず、本人の現在の学力、学習進度、得意・不得意、志望する小山高専、情報系への関心を踏まえて最適化する。本人が実際に毎日使い、入試本番で力を発揮できることを最優先にする。

目標は、世界最高峰の品質を目指す高専入試対策プラットフォーム。問題の正確性、過去問分析の深さ、解説の明快さ、図表の品質、教科別データベースの体系性、操作性、学習効果のすべてで妥協しない。「世界最高峰」は目標であり、達成済みと称するのではなく、検証と改善を継続する。


## 目的
会話内で提供された国立高等専門学校入学者選抜統一学力検査の原本PDFを、クラウド作業環境で読み込み、KNOT Study「高専絶対合格」の教材・問題演習・解説・要点まとめを改善する。

## 資料の扱い
- 原本PDFはユーザーがクラウド作業セッションに添付して分析する。
- この公開GitHubリポジトリには原本PDFを再アップロードしない。公開リポジトリは閲覧者を限定できる場所ではない。
- GitHubには、出典台帳、出題分析、独自に再構成した問題、独自作成図版、解説、テスト結果を反映する。
- 原本の文章・図表・レイアウトをそのまま転載しない。必要な場合は権利者の許諾条件を確認する。
- 原本に記載された訂正・不成立・全員得点などの措置を必ず確認する。


## GitHub上の過去問を一次資料として使うこと（必須）
- ユーザーは過去問資料をすでにGitHub上へアップロードしている。作業開始時にリポジトリ全体を確認し、過去問PDF・画像・正解・訂正通知・関連資料の保存場所を特定する。
- **GitHub上に存在する過去問資料を必ず読み込み、分析・教材開発・新規問題制作の根拠として使う。** 資料を確認せず、一般的な高専入試の知識だけで問題を量産しない。
- 既存の過去問ファイルを勝手に移動・削除・上書きしない。原本のファイル名、年度、教科、版、ページを出典台帳に記録する。
- PDFが画像主体ならページ画像も確認し、OCRテキストだけで図・表・数式・選択肢を判断しない。
- 問題冊子、正解、訂正通知を突き合わせ、公式の訂正・採点上の扱いを反映する。
- 過去問から抽出した出題傾向・単元・形式・難易度をもとに、本人の演習に使える新作問題・類題・発展問題を制作する。
- 原本そのものの公開・再配布と、出題内容を分析して独自の問題を作ることは区別する。公開リポジトリに原本を置く場合は、公開・再配布の権利が確認できているかを必ず確認する。許諾が不明なら原本はそのまま再掲せず、既存の保存場所を参照して独自問題・分析データを作る。

## 教科別問題データベース（必須）
問題を一つの巨大なJSONに雑然と詰め込まず、**教科ごとに独立したデータベース**を構築する。最低限、数学・理科・英語・国語・社会を別々に管理し、年度・単元・大問・難易度・出題形式などで横断検索できる構造にする。
- 教科別に問題データ、解説、図版、出典情報、タグ、品質検証結果を整理する。
- 例：`src/data/study/kosen/math/`、`science/`、`english/`、`japanese/`、`social-studies/` のように分離する。実際の既存構成を調べて、既存実装と整合する最適な配置を選ぶ。
- 共通スキーマを設け、問題ID、教科、単元、学習目標、難易度、問題文、選択肢、正答、解説、誤答解説、図版参照、出典、関連要点まとめ、作成・検証状態を管理する。
- 過去問を参考にした問題には、参照元の年度・教科・大問・小問・ページと、どの要素を参考にしたかを記録する。完全な独自問題は「KNOTオリジナル」と明示し、実際の過去問と誤認させない。
- 同じ問題の重複登録を防ぐため、安定したID、重複検出、改訂履歴を用意する。
- 教科別DBから、基本対策・過去問演習・弱点補強・ランダム演習へ必要な問題だけを読み込めるようにする。初期表示で全データを一括ロードしない。
- データベースの容量は5GBを超えても構わない。5GBを上限として問題や図版、解説、検証資料を削らない。ただし、容量を無目的に膨らませず、正確性・検索性・保守性・読み込み速度を両立する。大容量化する場合は教科・年度・用途ごとに分割し、遅延読み込み・索引・圧縮・重複排除を行う。
- GitHubのファイルサイズ制限やリポジトリ肥大化にも注意する。巨大な原本PDFや画像群を通常のGit履歴に無制限に積み上げない。必要ならGit LFSや適切な外部ストレージを検討し、サイト本体は軽量に保つ。利用可能な容量・権限・料金を確認せず、保存できると断言しない。

## 問題制作の方針
- GitHub上の過去問を年度・教科・大問・小問ごとに分析し、頻出テーマだけでなく、出題形式の変化、複合分野、資料読解、実験考察、典型的な思考手順も抽出する。
- その分析から、(1)過去問の狙いを踏まえた独自類題、(2)同じ知識を別の角度から問う問題、(3)基礎確認問題、(4)標準問題、(5)応用・発展問題を教科別に制作する。
- 過去問の数字や固有設定だけを機械的に置き換えた問題にしない。問う能力・考え方を理解したうえで、条件・選択肢・図表・誤答設計まで新しく構成する。
- 本人の現在の学力と小山高専合格目標を基準に、優先して解くべき問題を明確にする。易しすぎる問題ばかりにも、難問ばかりにも偏らせない。
- すべての問題に、解答根拠・詳しい解説・誤答の理由・関連要点まとめ・出典またはオリジナル表記を付ける。
- 問題制作後は、別工程で正答を再計算・再検証し、曖昧さ、複数正解、選択肢の不備、図表との不一致、解説の飛躍をチェックする。可能なら自動テストと人間による確認の両方を行う。


## クラウド作業AIへの実行指示（そのまま実行すること）
あなたは説明だけを返す相談役ではなく、このリポジトリを実際に調査・編集・検証する開発担当者として作業する。以下の順序を守る。

### フェーズ1：資料と現状の棚卸し
1. GitHubリポジトリ `knotspace/knotspace.github.io` の最新状態を取得し、ブランチ、ディレクトリ構成、Study関連実装、問題データ形式、既存の要点まとめ、テスト・ビルド手順を確認する。
2. GitHubにアップロード済みの過去問資料を全件探索する。PDFだけでなく、画像、正解、訂正通知、補足資料も確認する。
3. 各ファイルについて年度・教科・本試験/追試等の区分・ページ数・内容・読み取り可否を一覧化する。見つからない教科・年度は「未確認」と記録し、存在を推測しない。
4. 既存の問題データと過去問を照合し、重複、誤答、誤った出典、解説不足、未対応単元を洗い出す。
5. まず棚卸し結果と実装計画を短く報告し、その後に実装へ進む。資料の確認前に大量の問題を生成しない。

### フェーズ2：過去問の全問分析
1. 確認できた過去問を教科・年度ごとに、全大問・全小問まで分析する。
2. 各設問の問題形式、分野、必要知識、思考過程、難易度、標準性、重要度、想定解答時間、正答根拠を記録する。
3. 正解資料・訂正通知と照合する。採点上の特別措置も分析台帳に明記する。
4. OCRが不確かな箇所、図表が読めない箇所、資料間で矛盾する箇所は、原本ページを目視確認する。解決できない場合は不明として残す。
5. 年度間の共通点と変化をまとめ、本人が優先して学ぶ単元・解法を順位付けする。

### フェーズ3：教科別データベースの設計・構築
1. 数学・理科・英語・国語・社会の独立した問題DBを構築する。
2. 共通スキーマ、教科別タグ、出典台帳、難易度、学習目標、解説、誤答分析、要点まとめリンク、図版参照、検証ステータスを整備する。
3. 既存のStudy画面と互換性を保ち、既存機能を壊さない形で移行する。必要なら互換レイヤーを用意する。
4. 問題データは教科・年度・単元などで分割し、必要な範囲だけロードする。5GBを超えるデータ量も許容するが、GitHubの制限・ストレージ料金・デプロイ制限を確認し、適切な保管方式を選ぶ。
5. 原本PDFを公開リポジトリへ複製しない。既存ファイルを保全し、権利が確認できない原文・図版の転載は避ける。

### フェーズ4：高品質な問題制作
1. 過去問の分析結果を根拠に、基礎・標準・応用・発展の問題を教科別に作成する。
2. 過去問の表面だけを数字変更した問題にせず、問う力や考え方を抽出して新しい条件・設定・選択肢・図表で再構成する。
3. それぞれの問題に、唯一の正答、正答根拠、段階的解説、各誤答の理由、関連要点まとめ、難易度、想定時間、出典またはKNOTオリジナル表記を付ける。
4. 問題数はノルマにしない。品質検証に通った問題だけを公開DBに登録する。
5. 本人の現状に合わせ、合格に直結する標準問題を優先し、必要な基礎の穴埋めと段階的な応用も用意する。

### フェーズ5：品質保証・実装
1. 全問題の正答を独立して再計算・再確認し、複数正解、条件不足、誤植、選択肢の不備、図表との不一致を検出する。
2. JSON/データスキーマ、ID重複、出典参照、要点まとめリンク、画像参照、選択肢数、正答indexを自動検証する。
3. 基礎網羅問題と同じ回答体験を維持し、スマートフォンとPCの両方で表示・操作を確認する。
4. 初期ロードのサイズ、画面遷移、検索速度を計測し、大容量DBでも必要な問題だけを読み込む。
5. ビルド・テスト・ブラウザ確認を実行し、失敗は原因を修正する。未実行のテストを実行済みと報告しない。

### フェーズ6：GitHub反映と報告
1. 変更前に最新状態を確認し、既存のユーザー作成ファイルを削除・上書きしない。
2. 変更を意味のある単位でコミットし、差分を確認してから反映する。
3. 最終報告には、確認した過去問ファイル一覧、分析済み年度・教科・設問範囲、教科別DBの場所と件数、制作・検証済み問題数、変更ファイル、コミット、テスト結果、未解決事項を記載する。
4. GitHubに実際に反映していない内容を「完成」「アップロード済み」と表現しない。

**最優先事項：本人の受験に役立つこと、過去問資料に忠実であること、問題の正確性を担保すること。見た目や問題数だけで完成扱いにしない。**

## 最優先の開発対象
1. **高専基本対策モード**：計算量が比較的少ない知識・理解・資料判断・典型問題を中心に、質の高い四択演習を作る。
2. **過去問モード**：年度・教科・大問単位で本番に近い演習を行えるようにする。公式原文をそのまま再掲するのではなく、出題構造・難易度・学習目標を保った独自再構成問題を作る。
3. **数学β版**：令和7・8年度の数学大問1〜4を対象に、すでにある13問を原本と照合して正誤・出典・解説を再点検し、標準的で捨て問ではない小問を追加する。
4. **要点まとめ**：各問題の解説から、該当する要点まとめへ直接移動できるようにする。
5. **図版**：関数グラフ、動点、円・相似、格子点、立体の切断、理科の実験装置・グラフなどは、スマホでも読める独自SVG等で作成する。
6. **学習体験**：基礎網羅問題と同じ操作感・回答導線に統一し、進捗、正答率、復習、時間管理を使いやすくする。

## 過去問分析の手順
各年度・教科について、問題冊子と正解資料を照合し、全大問・全小問を一覧化する。各設問に以下を付ける。
- 年度、教科、大問、小問、配点
- 分野・単元・必要知識
- 出題形式（知識、計算、資料読解、実験考察、図形、記述等）
- 難易度、標準性、重要度、解答時間の目安
- 正答と根拠、誤答になりやすい理由
- KNOT教材への採否（採用／類題化／要点まとめのみ／対象外）と理由
- 参照した原本ファイル名・ページ

「過去問に出なかったから重要度が低い」と短絡しない。中学範囲の基礎、複数年度で繰り返す考え方、他の設問を解く前提知識は残す。一方、極端に特殊な難問や学習効果が低い細部は、採用しない理由を記録して優先度を下げる。

## 問題品質の基準
- 中学生が読んで意味を取り違えない自然な日本語にする。
- 四択の正解は必ず一つ。条件不足・複数正解・曖昧な表現を排除する。
- 選択肢の長さや正解位置の偏りを抑える。
- 正解だけでなく、考え方を段階的に説明する。
- 誤答選択肢ごとに、どこで間違えやすいかを説明する。
- 数学・理科は途中式、単位、図の読み方、条件の確認を明示する。
- 出典情報は実際に確認できた年度・大問・小問だけを書く。推測で出典を付けない。
- 問題・正答・解説・図版を別々に点検し、機械的なJSON検証も行う。

## GitHubでの作業ルール
- 作業開始時に最新ブランチと既存ファイルを確認し、現在の実装を壊さない。
- 既存の基礎網羅問題の回答UI・データ形式・共通CSSを優先的に再利用する。
- 原本PDFや原文のまとまった転載を公開リポジトリへ追加しない。
- 問題データは既存のJSON構造に合わせ、必要な場合だけスキーマを拡張する。
- 各問題に出典・解説・要点まとめリンクを付ける。
- 変更後はJSON構文、問題数、選択肢数、正答index、リンク先、重複ID、スマホ表示を確認する。
- ビルドやブラウザ確認を実行していない場合は、完了と断言しない。変更内容と未確認事項を報告する。

## 作業姿勢
